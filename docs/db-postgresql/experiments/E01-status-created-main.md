# E01 — `(status, created_at, id)` index on main

Round 1, PostgreSQL 18 (`postgres:18-alpine`, 4 CPU / 4 GB), SQL-level harness, warmup 5 + 20 reps, fresh `--prepare` per run.
Base = **main**; the `v1` column is shown for reference. Driver `harness/bin/round1-pg.sh`; variant order per label in
`results/logs/round1-pg.log` (S2: main first; S8-S2: E01b first; S4: E02b first, E01a 10th; S8-S4: E12 first; S5: E1Q first; S6: E01a first; S7: E02a first).
No run failed (no `failures-round1.txt`).

## Hypothesis

A status-leading index `(status, created_at, id)` lets the queue queries (`keys_*`, `oldest_*`) read only `NEW` rows in `created_at` order
instead of scanning/aggregating by `idx_outbox_record_status` and heap fetches. Three variants separate the index from the SQL change:

| Variant | DDL | Queries |
|---|---|---|
| `E01a` | main + `idx_outbox_record_status_created_id (status, created_at, id) INCLUDE (partition_no, next_retry_at, record_key)` (`experiments/E01a-status-created-main/ddl.sql`) | main catalog |
| `E01b` | as E01a (`experiments/E01b-status-created-main-v1queries/ddl.sql`) | main catalog, `keys_strict`, `keys_nonstrict`, `oldest_created`, `oldest_due_strict` replaced by the v1 SQL (`experiments/E01b-.../queries/`) |
| `E01c` | main + the same index **without INCLUDE** (`experiments/E01c-status-created-noinclude-main-v1queries/ddl.sql`) | as E01b (the query dirs are identical, `diff -r` empty) |

The DDL diffs to `outbox-wt-main`'s `schema/postgres/outbox-tables.sql` are exactly the one `CREATE INDEX` (verified). Main keeps both record-key indexes
(`idx_outbox_record_record_key_created`, `idx_outbox_record_record_key_completed_created`) and `idx_outbox_record_status`,
`idx_outbox_record_status_retry`, `idx_outbox_record_partition_status_retry`. v1 DDL differs: it has no `(record_key, created_at)` index, its record-key index is `(record_key, completed_at, created_at, id)`, and it adds the partial `(created_at, id) ... WHERE completed_at IS NULL`.

## Which queries use the new index (plans, `plans/*.txt` in each result dir)

| Variant | Plans containing `idx_outbox_record_status_created_id` |
|---|---|
| E01a | S2: `keys_strict`, `keys_nonstrict`, `oldest_created`, `oldest_due_strict`, `count_partitions`. S4: the four queue queries. S5: + `count_failed`. S7: + `ids_failed_before`, `count_partitions` (`E01a/postgres/<label>-R1/plans/`) |
| E01b | S2: only `oldest_created`, `count_partitions` (`keys_*` and `oldest_due_strict` stay on `idx_status` / `idx_status_retry`); S4, S5, S7: `keys_strict`, `keys_nonstrict`, `oldest_created` |
| E01c | S2: only `oldest_created`; S4, S5, S7: `keys_strict`, `keys_nonstrict`, `oldest_created` |

`oldest_due_strict` is never served by the new index in E01b/E01c (it uses `idx_outbox_record_status_retry`, ordered by `next_retry_at`, as in main/v1).

Plan excerpts (S4, 1 M NEW rows, `keys_strict`):

- main (`results/main/postgres/S4-R1/plans/keys_strict.txt`): `Parallel Hash Right Anti Join` of a `Parallel Seq Scan ... WHERE completed_at IS NULL` against `Parallel Index Scan using idx_outbox_record_status`, `GroupAggregate` + two `Sort`s, 1 000 000 rows, Execution 2568 ms.
- E01a (`results/E01a/postgres/S4-R1/plans/keys_strict.txt`): the same shape; only the inner scan becomes `Parallel Index Only Scan using idx_outbox_record_status_created_id` (Heap Fetches 0, buffers 16 953 instead of 112 338 for that node). Total 2412 ms. The main SQL (`GROUP BY record_key`, `MIN(created_at)`, `NOT EXISTS` predecessor) must visit every NEW row, so the index cannot bring it below seconds.
- E01b (`results/E01b/postgres/S4-R1/plans/keys_strict.txt`): `Limit -> Nested Loop Anti Join`, outer `Index Scan using idx_outbox_record_status_created_id` (`Index Searches: 1`, 6 buffers for 10 rows), inner `idx_outbox_record_record_key_created`; Execution 0.131 ms.

`keys_nonstrict` S2 with the v1 SQL (E01b, `results/E01b/postgres/S2-R1/plans/keys_nonstrict.txt`): the planner picks `Index Scan using idx_outbox_record_status` (1 000 of 1 200 index rows), a nested-loop anti join (1 000 probes on `idx_..._record_key_completed_created`), 4 212 buffers, 3.36 ms; the new index is not chosen because it cannot avoid fetching all due NEW rows. v1 reads 10 rows from its partial index and stops (253 buffers, 1.09 ms; `results/v1/postgres/S2-R1/plans/keys_nonstrict.txt`), main aggregates the same 1 000 rows in 0.92 ms (`results/main/postgres/S2-R1/plans/keys_nonstrict.txt`).

`oldest_created` S2: E01a `Index Only Scan` on the new index, main/v1 the older indexes; S4 215 ms (main) -> 0.4 ms (E01a), see table.

## Verdict

- **E01a (index only, main SQL): mixed, leaning no difference on P1.** `keys_strict` stays at seconds (S4 4411 -> 3964 ms, S5 14.7 s -> 14.6 s, S6 411 -> 388 ms, S7 55.9 -> 53.0 ms; all within noise). `keys_nonstrict` improves in S5 (116 -> 43.9 ms, -62 %), S6 (110 -> 19.5 ms, -82 %), S7 (8.6 -> 6.0 ms, -31 %) but is no difference in S2/S8-S2/S8-S4 and unreproducible in S4; the result is still 5-300x slower than v1. `pages`, `insert`, `upd_*`, `delete_by_id` no difference (S5 `pages` +34 % / +36 % / +29 % for E01a/E01b/E01c, 146 -> 195/198/188 ms: the `pages` plan is identical in all variants, `Parallel Index Scan using idx_outbox_record_status`, Execution 99.6 / 98.5 / 99.1 ms in `results/{main,E01a,E01b}/postgres/S5-R1/plans/pages.txt`, so it is not caused by the index; unexplained cache effect, flagged only). P2: `oldest_created` is a clear win in every large scenario (S4 215 -> 0.41 ms, S5 63.6 -> 0.39 ms, S6 85.5 -> 0.36 ms, S7 4.4 -> 0.39 ms; S2 1.17 -> 0.39 ms); `oldest_due_strict` only S5 (-48 %, still 2.7 s). Price: +150 MB (+48 % of index bytes) and +4-7 % WAL per write.
- **E01b / E01c (index + v1 SQL): the queue queries become fast (`keys_strict` S4 1.31/1.23 ms, S5 1.38/1.33 ms, S6 1.77/1.34 ms, S7 1.19/1.16 ms) but that is the v1 SQL, not the index**: v1 itself has 1.25 / 1.29 / 1.41 ms on S4/S5/S6 with its partial created_at-first index. The index's own contribution over v1 is S7 (v1 13.3 ms -> 1.2 ms: status-leading skips the 390 k FAILED entries the created_at-ordered index walks). In S2/S8-S2 `keys_nonstrict` is a **loss** vs main (+164 % 1.65 -> 4.35 ms; +119 % 0.91 -> 2.0 ms) and vs v1 (2.1 ms in S2) because the v1 non-strict SQL needs all due NEW rows here (see plan). `oldest_due_strict` -77 % ... -100 % in every scenario (this is the v1 SQL: `ORDER BY next_retry_at LIMIT 1` on `idx_status_retry`), `oldest_created` -32 % ... -100 %.
- **INCLUDE column list is not needed**: E01b vs E01c are equal in every P1/P2 cell above (all differences below the 0.15 ms / group thresholds) while E01c's index is 43 % smaller (82 MB vs 143 MB on S2).
- **Overall E01: mixed.** Main-SQL + index (E01a) is not a fix for the hot path; the worthwhile effect is `oldest_created` (P2, small absolute gain except at scale). With v1 SQL the status-leading index helps only where FAILED rows are numerous (S7) and otherwise duplicates what v1's own partial index does (see E02 for the comparison on v1).

## Portability

| Dialect | Equivalent |
|---|---|
| PostgreSQL | as measured (`INCLUDE` since PG 11); E01c form (no INCLUDE) is enough |
| SQL Server | `CREATE INDEX ... (status, created_at, id) INCLUDE (partition_no, next_retry_at, record_key)` works the same; the INCLUDE-less form is also valid |
| Oracle | no INCLUDE; add the covered columns as trailing key columns, or use the 3-column form (E01c). v1 already ships `(status, created_at, id, partition_no, next_retry_at, record_key)` for Oracle (`STATE.md` V1-2) |
| MySQL / MariaDB | no INCLUDE (InnoDB appends the primary key to every secondary index automatically); `(status, created_at, id)` possible, extra columns as trailing key columns. Not measured |
| H2 | no INCLUDE; plain composite index, small effect expected. Not measured |

## Follow-ups

- Do not add the index to main on its own; E02 evaluates it as a replacement for v1's queue index.
- `oldest_created` alone could be served by a cheaper structure if only P2 needed it (e.g. a partial index), but v1's own partial index already gives 0.64 ms on S4-S7 (v1 column).
- If `keys_nonstrict` S2 (v1 SQL) matters, test it against a status-leading partial index (E02b rows: 1.27 ms).
