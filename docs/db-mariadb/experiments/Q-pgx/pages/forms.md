# pages forms (pgx)
PG hypothesis transferred: the Postgres design relies on a partial index (`WHERE completed_at IS NULL`), INCLUDE columns, LATERAL probes and plan-cache tricks. On InnoDB/MariaDB there are no partial indexes (COMPLETED rows are in every index; `completed_at IS NULL` is a `ref_or_null`/range on the 2nd key part), no INCLUDE (covering = trailing key columns), the table is clustered on `id` (VARCHAR(255)) and every secondary entry carries it, there is no LATERAL, no extended statistics and no generic-plan flips. Portable lessons kept: no GROUP BY when an anti-join already yields one row per key, order by index order with LIMIT, `<=` conjunct before the tie-break, redundant `completed_at IS NULL`. Smoke test: all forms parse on MariaDB 12 and return the same rows as the branch SQL on a 30k-row toy table (not a performance statement).

Index names refer to the branch DDL (`idx_outbox_record_status_completed_created_id (status, completed_at, created_at, id, partition_no, next_retry_at, record_key)`, `..._key_completed_created_id (record_key, completed_at, created_at, id)`, `..._status_completed_retry (status, completed_at, next_retry_at, partition_no)`, `..._status_completed_partition (status, completed_at, partition_no)`). `FORCE/IGNORE INDEX` forms fail with error 1176 on any schema lacking the named index: HIGH RISK, measurement aid only. Baseline: `record_key IN (:recordKeys) AND status = :status AND completed_at IS NULL ORDER BY record_key, created_at, id`. PG failure mode (IN walks the status index with record_key as filter, BitmapAnd) has an InnoDB analogue in `index_merge` intersection and in choosing a status index over the key index. No LATERAL exists in MariaDB; unnest+LATERAL cannot be copied literally.
