# keys_strict forms (pgx)
PG hypothesis transferred: the Postgres design relies on a partial index (`WHERE completed_at IS NULL`), INCLUDE columns, LATERAL probes and plan-cache tricks. On InnoDB/MariaDB there are no partial indexes (COMPLETED rows are in every index; `completed_at IS NULL` is a `ref_or_null`/range on the 2nd key part), no INCLUDE (covering = trailing key columns), the table is clustered on `id` (VARCHAR(255)) and every secondary entry carries it, there is no LATERAL, no extended statistics and no generic-plan flips. Portable lessons kept: no GROUP BY when an anti-join already yields one row per key, order by index order with LIMIT, `<=` conjunct before the tie-break, redundant `completed_at IS NULL`. Smoke test: all forms parse on MariaDB 12 and return the same rows as the branch SQL on a 30k-row toy table (not a performance statement).

Index names refer to the branch DDL (`idx_outbox_record_status_completed_created_id (status, completed_at, created_at, id, partition_no, next_retry_at, record_key)`, `..._key_completed_created_id (record_key, completed_at, created_at, id)`, `..._status_completed_retry (status, completed_at, next_retry_at, partition_no)`, `..._status_completed_partition (status, completed_at, partition_no)`). `FORCE/IGNORE INDEX` forms fail with error 1176 on any schema lacking the named index: HIGH RISK, measurement aid only. Baseline: branch SQL (correlated NOT EXISTS with the `<=` conjunct), ordered by `(created_at,id)` LIMIT :limit.

| form | idea | why it may win on MariaDB | access path | risks | MySQL |
|---|---|---|---|---|---|
| ks_leftjoin | `LEFT JOIN earlier ... WHERE earlier.id IS NULL` | MariaDB executes NOT EXISTS as a dependent subquery (no anti-join transformation until MDEV work in later versions), a LEFT JOIN with IS NULL gets "not exists" optimization (stops at first match) and lets the optimizer choose join order. | outer: status/completed_at/created_at/id key (ordered, covering); inner: key index range on (record_key, completed_at IS NULL, created_at). | optimizer may reorder and break the ORDER BY index (filesort). Rows equal because `earlier.id` is NOT NULL. | yes |
| ks_split | two NOT EXISTS: `created_at <` and `created_at = AND id <` | removes the OR so each subquery is a pure range (no `index_merge`/OR-range doubt); PG notes the OR hides the range. | key index, two single-range probes; second only when the first passes. | two probes per candidate (cost when many candidates pass); same rows. | yes |
| ks_head | `o.id = (SELECT e.id ... incomplete ORDER BY created_at,id LIMIT 1)` | "o is the first incomplete row of its key"; one ordered LIMIT 1 probe in the key index, no range condition on o's columns at all. | key index (record_key, completed_at, created_at, id): index-only. | o is incomplete so equality is exact; dependent subquery per candidate. | yes |
| ks_window | `ROW_NUMBER() OVER (PARTITION BY record_key ...)` over all incomplete rows, keep rn=1 | one pass instead of per-candidate probes; good only if the incomplete set is small (S2/S5), catastrophic on S4 (1M NEW, materialised, filesort; toy EXPLAIN shows derived table + filesort). | scans status index fully, no early stop. | pushes `partition_no IN` into the derived table: valid only because all rows of a key share one partition (PartitionHasher), not enforced by the schema. Cannot honor LIMIT early. | MySQL 8 only |
| ks_tuple | `(earlier.created_at, earlier.id) < (o.created_at, o.id)` | shortest, PG-style tuple compare. | MariaDB does not turn row inequality into a range (MySQL 8 partly does), so expect key-index range on record_key only + filter. | probably slower than base; included to measure. | partial |
| ks_force | base with FORCE INDEX on outer and subquery | pins the early-stop ordered scan and the probe index, defending against a plan flip to the wide indexes. | as base. | HIGH RISK (schema must have both names). | yes |
