# oldest_created forms (pgx; NEW/FAILED, `completed_at IS NULL` required)
PG hypothesis transferred: the Postgres design relies on a partial index (`WHERE completed_at IS NULL`), INCLUDE columns, LATERAL probes and plan-cache tricks. On InnoDB/MariaDB there are no partial indexes (COMPLETED rows are in every index; `completed_at IS NULL` is a `ref_or_null`/range on the 2nd key part), no INCLUDE (covering = trailing key columns), the table is clustered on `id` (VARCHAR(255)) and every secondary entry carries it, there is no LATERAL, no extended statistics and no generic-plan flips. Portable lessons kept: no GROUP BY when an anti-join already yields one row per key, order by index order with LIMIT, `<=` conjunct before the tie-break, redundant `completed_at IS NULL`. Smoke test: all forms parse on MariaDB 12 and return the same rows as the branch SQL on a 30k-row toy table (not a performance statement).

Index names refer to the branch DDL (`idx_outbox_record_status_completed_created_id (status, completed_at, created_at, id, partition_no, next_retry_at, record_key)`, `..._key_completed_created_id (record_key, completed_at, created_at, id)`, `..._status_completed_retry (status, completed_at, next_retry_at, partition_no)`, `..._status_completed_partition (status, completed_at, partition_no)`). `FORCE/IGNORE INDEX` forms fail with error 1176 on any schema lacking the named index: HIGH RISK, measurement aid only. PG note: MIN vs ORDER BY LIMIT 1 were equal in execution on PG. On MariaDB the difference may be real: with the 7-column index the `partition_no` filter is a later key part, MariaDB cannot do a loose/"optimized away" MIN with it (toy EXPLAIN shows plain `ref` for both), so `MIN` must read all matching entries while `ORDER BY created_at LIMIT n` stops at the first row passing the partition filter. With 1/4 partition ownership the first match is usually within a few entries. Result-shape difference: MIN yields one row (NULL if none), ORDER BY LIMIT yields zero rows if none.
