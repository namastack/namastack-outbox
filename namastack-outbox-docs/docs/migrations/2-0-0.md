# Upgrade to 2.0.0

Upgrade from **1.11.1** using your existing database. Tables, payloads, handler IDs
and retry state stay in place; pending records can be processed after the upgrade.

## 1. Update dependencies {#dependencies}

Set `io.namastack:namastack-outbox-bom` to **2.0.0** and remove explicit 1.x versions
from individual Namastack modules. JDBC and MongoDB starter names are unchanged.
Replace these removed modules if you use them:

| Remove | Use instead |
|---|---|
| `namastack-outbox-starter-jpa` | `namastack-outbox-starter-jdbc` |
| `namastack-outbox-jpa` | `namastack-outbox-jdbc` |
| `namastack-outbox-metrics` / `namastack-outbox-tracing` | `namastack-outbox-observability` |

**JPA applications:** keep your business entities, Spring Data JPA and
`JpaTransactionManager`. JDBC outbox persistence must use the **same DataSource**.
Point JDBC at your existing physical table names if Hibernate used custom naming;
see [persistence configuration](../reference/persistence.md#custom-schema-name-and-table-prefix).
Remove explicit references to the old Namastack JPA entities and dialect.

**Metrics users:** update legacy meter names and tags using the
[current metric list](../reference/observability.md#gauge-metrics).
Completed-record counts now require
`namastack.outbox.observability.metrics.record-statuses: [NEW, FAILED, COMPLETED]`.

## 2. Rename deprecated properties {#configuration}

All paths below are relative to `namastack.outbox`. Skip this step if you already
use the replacement names.

| Old property | Replacement |
|---|---|
| `poll-interval` | `polling.fixed.interval` |
| `batch-size` | `polling.batch-size` |
| `rebalance-interval` | `instance.rebalance-interval` |
| `processing.publish-after-save` | `multicaster.publish-after-save` |
| `processing.shutdown-timeout-seconds` | `processing.shutdown-timeout` |
| `instance.heartbeat-interval-seconds` | `instance.heartbeat-interval` |
| `instance.stale-instance-timeout-seconds` | `instance.stale-instance-timeout` |
| `instance.graceful-shutdown-timeout-seconds` | `instance.graceful-shutdown-timeout` |

Convert values from `*-seconds` to durations: **`30` becomes `30s`**. Carry over the
old property's effective value and update all configuration sources, including
environment variables. Removed properties can be **silently ignored**.

## 3. Add the new database indexes {#database}

**JDBC and JPA → JDBC:** add a new Flyway migration or Liquibase changeset using the
[SQL for your database](2-0-0-indexes.md). Keep previously applied migrations and
existing tables unchanged. With migration tooling, set:

```yaml
namastack:
  outbox:
    jdbc:
      schema-initialization:
        enabled: false
```

**MongoDB:** no collection or index migration is required.

## 4. Deploy and verify {#deployment}

Rehearse on a database copy. For a rollout with a maintenance window:

1. Back up the database, pause producers and gracefully stop the old instances.
2. Apply the index migration and start 2.0.0 against the same database.
3. Confirm that existing pending records and due retries reach their handlers and
   downstream systems, then resume producers.
4. Check that new business writes and outbox records commit or roll back together.

Keep payload classes, handler IDs, serializer and retention settings unchanged during
this rollout. Keep `processing-groups.enabled=false` (the default) until every worker
has upgraded; adopt named groups separately. For rolling upgrades and rollback
requirements, follow [Rolling Deployments](../reference/rolling-deployments.md).
Retain the old indexes through the rollback window.

## Other changes to check

| Change | Action, if relevant |
|---|---|
| Scheduling now rejects calls without an active Spring transaction. | No change for applications already scheduling transactionally. |
| Generated IDs and keys now use UUIDv7. | Accept both UUIDv4 and UUIDv7; existing IDs and string columns stay unchanged. |
| Equal creation timestamps are ordered by record ID. | Avoid relying on handler declaration order for timestamp ties. |
| Adaptive polling validates its intervals. | Use `min-interval >= 1ms` and `max-interval >= min-interval`. |
| State metrics are collected asynchronously. | Treat `NaN` as unknown, not zero; see [Observability](../reference/observability.md). |

## Custom extensions and tests {#extension-and-test-code}

<details>
<summary>Only if you use repository APIs or construct Core objects directly</summary>

Rebuild these modules against 2.0.0 and update the affected APIs:

| Old API | Replacement |
|---|---|
| `OutboxRecordStatusRepository` | `OutboxRecordRepository` |
| `save(record)` | `create(record)` for new records; duplicate IDs must fail. |
| `update(record)` | `updateProcessingState(record)`; update only processing fields and return `false` for missing rows. |
| `findRecordKeysInPartitions(..., status, ...)` | Remove the `status` argument; the query selects due `NEW` records. |
| Java `OutboxRecordMetadata` constructor | Add trailing `recordId` and `processingGroup` arguments, e.g. `null, "default"` for scheduling fixtures. |
| Java `OutboxFailureContext` constructor | Add trailing `processingGroup`, e.g. `"default"`. |

Custom repositories must also implement `findIncompleteRecordPages`,
`findOldestCreatedAtByPartitions` and `findOldestDueNextRetryAtByPartitions`.
Pages must include future `NEW` retries, preserve `(createdAt, id)` ordering, and
include an empty page for requested keys with no records. The oldest-due query must
match polling's eligibility rules. Follow the interface contracts when implementing
these methods. Kotlin metadata constructors provide defaults for the added fields.

Direct Java construction of messaging handlers also needs the new Boolean settings;
see [messaging constructors](../reference/messaging.md#direct-handler-construction-in-200).

</details>
